# Server-side evidence for `7.ssh.txt`

Sanitized excerpt from the server's log around the same time window as `7.ssh.txt` (all IPs, UUIDs, and hostnames below are placeholders, not real values). Two distinct problems show up.

## 1. Sessions dying seconds after auth with `SshEncoding: length invalid`

```
INFO tunnel2tunnel_ssh: SSH: new connection peer_ip=<redacted-ip> conn_id=<redacted-uuid>
INFO tunnel2tunnel_ssh: SSH: auth attempt (publickey) peer_ip=<redacted-ip> user=<redacted-uuid> fp=SHA256:<redacted>
INFO tunnel2tunnel_ssh: SSH: auth accepted entity_id=<redacted-uuid> entity_name="ExampleClient" peer_ip=<redacted-ip> fp=SHA256:<redacted>
INFO tunnel2tunnel_ssh: SSH: connection closed (authenticated) entity_id=<redacted-uuid> entity_name="ExampleClient" peer_ip=<redacted-ip>
WARN tunnel2tunnel_ssh: SSH: session ended with error err=SshEncoding: length invalid
```

This pattern repeats every 5-40 seconds for the same client across dozens of reconnect attempts. The client only has its chat/welcome session channel open at the time (`7.ssh.txt` shows the welcome banner printing, then the connection dying) — no tunnel/forwarding traffic is involved yet. The client's `ssh -v` config uses `ServerAliveInterval=3`, so `keepalive@openssh.com` global requests start arriving within a few seconds of auth; `SshEncoding: length invalid` is `ssh_encoding::Error::Length`, which `russh` raises from its own `String::decode`/`u32::decode` calls while parsing an incoming packet. The negotiated cipher/compression line (`compression: zlib@openssh.com` in both directions) points at `russh` 0.61.2's delayed-zlib compression path corrupting packet framing shortly after auth — a library-level issue, not anything this server hand-encodes. **Fix:** the server's `russh::server::Config::preferred.compression` is now pinned to `[none]` so this negotiation never happens (`crates/tunnel2tunnel-ssh/src/lib.rs`).

## 2. `direct-tcpip` rejected — target hostname not found

```
INFO tunnel2tunnel_ssh: direct-tcpip: channel open request client_entity=<redacted-uuid> client_entity_name="ExampleClient" peer_ip=<redacted-ip> host="example-host" port=5900
INFO tunnel2tunnel_ssh: direct-tcpip: rejected — target hostname not found (not a UUID or known alias) host="example-host" port=5900 client_entity=<redacted-uuid>
```

The client's `-L` command used the *display name* of the target entity ("example-host" above) as the SSH forward hostname — exactly what the frontend's generated SSH command shows. The backend's `resolve_target_entity` previously only accepted a UUID or a configured `entity_access.hostname` alias, never a plain entity name, so this always failed. **Fix:** `resolve_target_entity` now also falls back to an entity-name lookup (`Entity::find_unique_id_by_name`), succeeding whenever the name is unambiguous; a name shared by more than one entity is still treated as unresolved rather than guessed.
